# Database boundaries

`DATABASE_URL` is a non-owner login inheriting the pre-provisioned `bump_runtime` role. The API must call `assertRuntimeRole` at startup. `MIGRATION_DATABASE_URL` is a separate privileged migration credential, used only by migration and test fixture tools. Role/login provisioning happens outside application migrations; production operators must provision these roles and credentials before deployment.

Better Auth owns the seven identity tables and their permission checks. Tenant resources use `withTenant(database, { organizationId, userId }, callback)`: derive the user ID from a validated session, never a request body. The helper verifies and locks the current membership, sets transaction-local PostgreSQL context, and passes its transaction and authoritative role to the callback. All tenant queries must use that transaction. `setTenantContext` supports existing transactions that also contain a Better Auth operation. A membership lock prevents another transaction from revoking that membership during the operation.

The reviewed SQL appended to `0001_identity_tenancy.sql` defines runtime grants and row-security policies. **Drizzle snapshots describe table structure only; they do not capture these manually maintained grants or policies.** Review future generated SQL for unintended RLS changes. Never use schema push against a shared database. Both tenant tables force RLS; policies require current organization membership as well as matching tenant/user context. Settings writes and audit reads require owner/admin. Audit insert requires the actor to match the scoped user. Runtime roles cannot update, delete, or truncate audit events. Audit insertion by members must not request `RETURNING`, since they cannot read audit rows.

Audit records retain actor IDs and restrict organization deletion; the identity layer disables organization deletion for this slice. These controls protect against ordinary application queries and missing tenant filters. A compromised migration credential or a runtime process able to impersonate arbitrary users is outside this isolation boundary. Full evidence integrity, retention, and administrative recovery belong to later PRs.

Integration tests require an independently provisioned runtime URL, a privileged migration URL, `NODE_ENV=test`, and database names ending in `_test`. They seed synthetic users and delete only their own fixture rows using the migration connection.

Migration `0002_engagement_authorization.sql` adds the engagement head, immutable version declarations, and immutable owner approvals. All three tables force RLS and allow current members to read their own organization's records. Owners and administrators may create declarations; only owners may approve the current unrevoked revision, using their own actor ID. Composite foreign keys bind versions and approvals to the same organization. Runtime roles cannot update, delete, or truncate versions or approvals. Head updates are limited to revision/revocation columns; revoked heads remain readable and cannot be changed by the runtime. Database checks enforce positive revisions, complete revocation metadata, ordered validity timestamps, and lowercase SHA-256 format. Scope validation, content hashing, revision sequencing, and current approver authority during decisions belong to the shared policy and API transaction boundary.

The engagement policies and grants are reviewed SQL, also outside Drizzle snapshots. API operations serialize each head using a transaction advisory lock before reading it; ordinary member reads must not use `SELECT FOR UPDATE/SHARE`, whose update-policy requirements would hide member-visible or revoked records. Approval records are evidence of an explicit decision, not transferable execution permits. No execution is implemented in this slice.
